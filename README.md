**WalT** project allows to build **highly configurable platforms for network experiments**.

This repository allows to build official WalT OS images and publish them on the docker hub.

**Check-out the [website](https://walt-project.liglab.fr) for more info.**

## Building images

Clone this repository with its submodule:
```
$ git clone --recurse-submodules <repository-url>
```
(or run `git submodule update --init` in an existing clone.)

Then run `make` to build all images, or for instance
`make build.debian.rpi32` or `make build.featured.rpi32-chirpstack`
to build a single one.

Raspberry Pi images embed boot files (u-boot builds, firmware files)
generated by repository [walt-node-boot](https://github.com/drakkar-lig/walt-node-boot),
which is included as the git submodule `walt-node-boot`.
These files are taken from docker image
`waltplatform/rpi-boot-builder:<walt-node-boot-commit>`: if this image is
not available locally, `build.py` tries to pull it from the docker hub,
and otherwise builds it (this compiles u-boot, so it may take a while).
To use other boot files, update the submodule commit; uncommitted changes
in `walt-node-boot/rpi` are also taken into account (image tag
`<commit>-dirty`).

Some featured images are based on a base image of this repository (e.g.,
`rpi32-rtk-base` is based on `rpi32-debian`). When building such an image
alone, the local version of the base image is used, or, if missing, it is
built first. Run `make` (or build the base image first) to rebuild it.

The versions of some external software installed in the images (k3s,
RTKBase) are pinned in `env.py` (`PINNED_VERSIONS`).

## Image architecture

The images built for ARM boards (Raspberry Pi, NanoPi) declare platform
`linux/amd64` in their metadata (`pc-x86-32-alpine` declares `linux/386`,
inherited from its base image), even if their content is ARM. This is
intended: `build.py` does not pass option `--platform` to `docker build`,
which records the platform of the build host, even if the last stage of the
Dockerfile is `FROM --platform=linux/arm64 scratch` for instance.

This is consistent with the meaning of the image platform: it tells which
docker hosts can run the image as a container. WalT nodes never run
containers of these images, they boot them over the network. The only
docker hosts which run containers of a WalT image are WalT servers (for
`walt image shell`, and for the `RUN` instructions of `walt image build`),
and they are `linux/amd64` machines (ARM binaries run there through
qemu-user emulation).

We tried to declare the real platform (`linux/arm/v6`, `linux/arm64`, etc.).
It works for cloning, booting, `walt image shell` and `walt image build`,
but podman then prints warnings such as `image platform (linux/arm64) does
not match the expected platform (linux/amd64)`. A walt server could pass
option `--platform` to podman to avoid them, but older walt servers would
still print them, and multi-stage user Dockerfiles in `walt image build`
would be affected. So the architecture of an image is given by its node
models (label `walt.node.models`), and by its description on the docker hub
when useful (see `BASE_IMAGE_LONG_DESC_NOTES` in `env.py`).

## Testing images

`tests/smoke.sh <image> <node>` boots a WalT node on a locally built image
and runs a few checks on it (network root filesystem, server reachability,
clock, failed systemd units, internet access if the node has
`netsetup=NAT`, and the image-specific checks of `tests/checks/<image>.sh`
if this file exists). For instance:
```
$ tests/smoke.sh rpi32-debian my-rpi-node
```
The image is cloned as WalT image `smoke-<image>` (option `-n` selects
another name) and the script stops if other nodes use this WalT image,
since cloning reboots them. See the header of `tests/smoke.sh` for the
other options.
